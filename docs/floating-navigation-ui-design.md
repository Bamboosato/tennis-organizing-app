# Topパネル フローティングナビゲーション UI改善 設計仕様書

作成日: 2026-05-29

現行実装との整合確認日: 2026-10-06（package version `1.1.0`）

本書のURL別画面、フローティングナビゲーション、シングルス対応は実装済み。実装の中心は `src/app/AppClientShell.tsx` と共通layout。以下のテスト観点は確認対象を示し、実ブラウザーでの検証済み一覧ではない。

## 1. 目的

`tennis-organizing-app` のトップ領域をフローティングナビゲーション化し、ホーム、メンバー登録、対戦表作成をURL付きの独立画面として扱える構成にする。

変更前にホームへ混在していた説明、メンバー登録導線、ダブルス対戦表作成機能を分離した。現行ホームは説明と各機能への入口、条件入力と結果は形式別画面で提供する。

## 2. 確定URL

| URL | 画面 | 概要 |
| --- | --- | --- |
| `/` | ホーム画面 | アプリ説明、各機能概要、各機能へのリンクを表示する |
| `/members` | メンバー登録画面 | 既存のメンバー登録、編集、一覧機能を表示する |
| `/matchups/doubles` | ダブルス対戦表作成画面 | 既存のダブルス対戦表作成機能を表示する |
| `/matchups/singles` | シングルス対戦表作成画面 | ダブルスと同様の条件入力を表示し、対戦モードなしでシングルス対戦表を作成する |

## 3. 認証・アクセス制御

ログインユーザーのみ利用できる画面へ未ログイン状態で直接アクセスした場合は、一律でログイン画面を表示する。

今後、メンバー登録以外にも保護画面が増える可能性があるため、画面ごとの個別分岐ではなく、共通フォールバックとして設計する。

未ログイン時もアクセス先URLを維持し、共通シェルがログイン画面を表示する。メールログイン後に同じURLの機能画面を表示する。別URLへのリダイレクトは行わない。

Guestユーザーはログイン済み状態として扱う。ただし、メンバー登録は利用不可とする。

Guestユーザー向けの扱い:

- メンバー登録タブは非活性にする。
- ホーム画面に、メンバー登録はログインユーザーのみ利用できる旨を記載する。
- 対戦表作成は既存通り利用可能とする。
- ログイン済みGuestが `/members` へ直接アクセスすると、登録ユーザー限定の説明とホーム・ログアウト導線を表示する。`/members` のログイン画面からGuestで開始した場合はホームへ移動する。

## 4. Topパネル

PC・スマホ共通でフローティングパネルとする。参照UIは `tennis-matchup-app` のフローティングヘッダー方針に合わせる。

表示要素:

- 既存アプリアイコン
- アプリ名 `tennis-organizing-app`
- ナビゲーションタブ
- ログイン中のアカウント名
- アカウントアイコン

既存のタイトル・サブタイトルはTopパネルから削除し、新ホーム画面の説明文へ移動する。

## 5. PC表示仕様

Topパネル内で、アプリロゴ右側かつアプリ名下側にタブを配置する。

タブはシンプルモダンなデザインとし、強いタブ形状は避ける。

タブ構成:

- ホーム
- メンバー登録
- 対戦表 `ChevronDown`
  - ダブルス
  - シングルス

右側にはログイン中アカウント名を表示する。メールアドレスの場合は `@` の左側のみ表示する。

アカウントアイコン押下でアカウントモーダルを表示する。

## 6. スマホ表示仕様

Topパネルは画面上部に固定表示する。

Topパネル右側にハンバーガーメニューを配置する。

ハンバーガーメニューは画面全体表示とする。表示中は背景スクロールを抑止する。

将来的にメニュー項目が増えて画面内に収まらないケースを想定し、メニュー内容側はスクロール可能な構造にする。

メニュー内表示:

- Topのフローティング表示を維持する。
- ハンバーガーアイコンの位置には `x` ボタンを表示する。
- `x` ボタン押下でメニューを閉じる。
- アプリアイコン押下でホーム画面へ遷移する。
- メンバー登録
- 対戦表 `ChevronDown`
  - ダブルス
  - シングルス
- アカウントアイコン押下でPCと同じアカウントモーダルを表示する。

## 7. アカウントモーダル

PC・スマホ共通のモーダルとして実装する。

ログイン中の表示:

- メールアドレスを表示する。
- ログアウトボタンを配置する。
- ログアウト押下時は既存のログアウト動線を利用する。

ログアウト操作は入力条件・結果・メンバー編集状態を初期化し、現在のURL上にログイン画面を表示する。ホームURLへ移動する処理ではない。

アカウントアイコン:

- メールアドレス先頭1文字の丸アイコンとする。
- プロフィール画像アップロードや外部画像表示は今回対象外とする。

## 8. ホーム画面

`/` に新規ホーム画面を作成する。

表示内容:

- Topパネルから移動したアプリ説明文
- `テニスサークル運営サポート` の説明文
- 各機能の概要説明
- 各機能へのリンク

説明対象:

- メンバー登録
- ダブルス対戦表作成
- シングルス対戦表作成

Guestユーザー向けに、メンバー登録はログインユーザーのみ利用可能である旨を明記する。

## 9. メンバー登録画面

`/members` に既存のメンバー登録機能を配置する。

既存機能として維持するもの:

- メンバー登録
- メンバー編集
- メンバー一覧
- メンバー非表示
- 登録順 / アイウエオ順の並び替え

フォームの入力・編集中IDは共通シェルで保持するため、同一セッション内のタブ移動では残る。保存成功、編集キャンセル、ログアウト操作で初期化する。画面を移動するだけで編集状態が破棄される仕様ではない。

現状の「ホームへ」ボタン付きパネルは完全削除する。

画面移動はTopパネルのナビゲーションに集約するため、画面内の戻る導線は不要とする。

Guestユーザーの場合、メンバー登録画面へは入れない。共通フォールバックまたは非活性タブにより、ログインユーザーのみ利用できる画面として扱う。

## 10. ダブルス対戦表作成画面

`/matchups/doubles` に既存の対戦表作成機能を配置する。

対象範囲:

- 現状の `Conditions` 以下の条件入力画面
- 参加メンバー選択
- ゲスト人数入力
- 対戦モード選択
- 対戦表作成
- 作成結果表示
- PDF出力

現在ホーム画面にある説明カードとメンバー登録ボタンは廃止する。

同一セッション中は、ダブルス画面の入力条件・作成結果を保持する。

## 11. シングルス対戦表作成画面

`/matchups/singles` にシングルス対戦表作成機能を配置する。

大きな機能差分は、ダブルス固有の対戦モードを使わない点と、1コートあたり2人で対戦する点とする。画面構成、参加者選択、結果表示、PDF出力の操作感はダブルスと共通化する。

対象範囲:

- `Conditions` 以下の条件入力画面
- 参加メンバー選択
- ゲスト人数入力
- コート数入力
- 実施回数入力
- 対戦表作成
- 作成結果表示
- PDF出力

ダブルスとの差分:

- 対戦モード選択は表示しない。
- `matchFormat: "singles"` を生成APIへ渡す。
- 1コートあたりの人数は `2` として扱う。
- 参加人数の最小値は `2` とする。
- 使用可能コート数は `floor(参加人数 / 2)` で算出する。
- コート数が参加人数に対して多い場合は、ダブルスと同様に使用可能コート数へ調整確認する。

参加者・性別表示:

- Guest入力はダブルスと同様に女性人数・男性人数を分ける。
- 登録メンバーの性別、追加Guestの性別は参加者情報として保持する。
- シングルスの組合せ生成では性別を評価条件に使わない。
- 結果表示とPDFでは、ダブルスと共通の表示仕様として `ゲスト09 M`、`佐藤 F` のように性別記号を表示する。
- 参加メンバー入力欄の横にダブルスと同様に女性 / 男性の内訳を表示する。Summaryには参加者数・使用可能コート数・実施回数と、ゲストがいる場合の採番内訳を表示する。

結果表示:

- コートカードはペアA / ペアBではなく、1対1の対戦として表示する。
- 表示例は `ゲスト01 F vs ゲスト09 M` のようにする。
- 休憩者表示はダブルスと同じ導線・見た目を維持する。

PDF出力:

- ダブルスと同じPDF出力導線を利用する。
- シングルスでは1コート1試合として `player1 vs player2` を出力する。
- 参加者名には画面表示と同じく性別記号を付与する。
- ファイル名にはシングルスであることが分かるラベルを含める。

同一セッション中は、シングルス画面の入力条件・作成結果をダブルスとは別に保持する。

## 12. 状態管理方針

URL付き画面へ移行するが、同一セッション中の画面状態は保持する。

状態保持方針:

- ダブルス画面の入力条件・作成結果は `/matchups/doubles` 用の状態として保持する。
- シングルス画面の入力条件・作成結果は `/matchups/singles` 用の状態として保持する。
- ダブルスとシングルスの状態は混在させない。
- タブ移動では状態を保持する。
- ブラウザリロード時の状態永続化は今回要件外とする。
- 状態は共通シェルのReact stateで保持し、リロード・ログアウト操作で初期化する。Firebase認証状態の保持とは別に扱う。
- 並び順設定、メンバー編集フォーム、PDF出力中状態・エラーはシェル共通であり、形式別条件・結果とは保持単位が異なる。

必要になった場合は、別途 `localStorage` 等による永続化設計を検討する。

## 13. テスト観点

### 13.1 機能観点

- 各URLで正しい画面が表示されること。
- PCタブで画面遷移できること。
- スマホメニューで画面遷移できること。
- 対戦表メニューを開閉できること。
- 対戦表メニューからダブルス、シングルスへ遷移できること。
- シングルスで対戦モードなしの条件入力から対戦表を作成できること。
- シングルスでPDFを作成できること。
- アカウントモーダルを開閉できること。
- ログアウトが既存動線通り動作すること。

### 13.2 認証観点

- 未ログインで保護画面へ直接アクセスするとログイン画面を表示すること。
- ログイン後にアクセスしようとしていた画面へ戻ること。
- Guestではメンバー登録タブが非活性になること。
- Guest向け説明がホーム画面に表示されること。
- ログアウト後、認証依存状態がリセットされること。

### 13.3 データ観点

- メールアドレスの `@` 左側のみがTopパネルに表示されること。
- アカウントモーダルではメールアドレス全体が表示されること。
- Guestの場合、アカウント表示が破綻しないこと。
- ダブルスの入力条件・作成結果がタブ移動後も同一セッション中に保持されること。
- シングルスの入力条件・作成結果がタブ移動後も同一セッション中に保持されること。
- ダブルスとシングルスの入力条件・作成結果が混在しないこと。
- シングルスのGuest人数入力が女性人数・男性人数を分けて保持されること。
- シングルス結果とPDFで `ゲスト09 M` のように性別記号が表示されること。

### 13.4 UI観点

- PCでTopパネルがフローティング表示されること。
- スマホでTopパネルが固定表示されること。
- 本文が固定Topパネルに隠れないこと。
- スマホメニュー表示中に背景スクロールしないこと。
- スマホメニュー内容が増えても、メニュー内スクロールで表示が破綻しないこと。
- アカウントモーダルがPC/スマホとも画面外にはみ出さないこと。
- タブ、メニュー、モーダルのフォーカス状態が視認できること。
- シングルスでは対戦モードが表示されないこと。
- シングルスの結果カードがペアA / ペアBではなく1対1表示になること。

### 13.5 状態遷移観点

- `/` から `/members`、`/matchups/doubles`、`/matchups/singles` へ遷移できること。
- `/members` から他画面へ遷移して戻ると入力・編集状態が保持され、保存成功・編集キャンセル・ログアウト操作で初期化されること。
- `/matchups/doubles` から他画面へ遷移して戻った場合、入力条件と作成結果が保持されること。
- `/matchups/singles` から他画面へ遷移して戻った場合、入力条件と作成結果が保持されること。
- `/matchups/doubles` と `/matchups/singles` を往復しても、それぞれの入力条件と作成結果が別々に復元されること。
- ログアウト後は現在URLでログイン画面を表示し、保護画面の内容を表示しないこと。
- メールログイン後の表示画面が、ログイン前に直接アクセスしたURLに対応すること。

### 13.6 非機能観点

- PC、タブレット、スマホ幅でレイアウトが破綻しないこと。
- 低速端末やスクロール中でも固定Topパネルが本文操作を阻害しないこと。
- メニュー、モーダル、トースト、参加者選択ドロップダウンの `z-index` が競合しないこと。
- 画面内メニューの開閉やルート遷移がタイミング依存で不安定にならないこと。
- シングルス生成時もAPI通信、PDF作成、画面遷移が非同期タイミングに依存して不安定にならないこと。

## 14. 実装時の作業順序（実装済み）

以下は実装時の作業分解を保存したもの。現在の未着手一覧ではない。既存の自動E2EはPWA関連に限定され、ナビゲーション・ログイン・シングルス生成操作全体のブラウザー検証は別途必要とする。

1. URL別画面構成と共通シェルの設計を追加する。
2. 認証フォールバックを共通化する。
3. Topパネルを専用コンポーネント化する。
4. 新ホーム画面を追加する。
5. 既存ホームの対戦表作成部分を `/matchups/doubles` へ移動する。
6. メンバー登録画面の上部パネルを削除する。
7. PC/スマホ表示、ハンバーガーメニュー、アカウントモーダルを調整する。
8. `matchFormat` を追加し、ダブルス / シングルスの生成条件を分離する。
9. ダブルス用状態とシングルス用状態を分離する。
10. 対戦表作成画面を共通化し、シングルスでは対戦モードを非表示にする。
11. API proxyの入力検証を `matchFormat` と試合形式別の参加人数最小値に対応させる。
12. 結果表示を `pairA` / `pairB` と `singlesMatch` の両方に対応させる。
13. PDF出力をシングルスの1対1表示と性別記号表示に対応させる。
14. lint、typecheck、build、必要に応じてPlaywrightで表示確認する。

## 15. 対象外

今回対象外とするもの:

- ブラウザリロード後の入力状態永続化
- プロフィール画像アップロード
- 外部アカウント連携
- 今回定義した以外の新規メニュー項目追加
  - 例: 設定、ヘルプ、操作ガイド、管理画面、お知らせ等
- ダブルスの対戦モード仕様変更
- ダブルスの結果表示、PDF出力仕様の不要な変更
