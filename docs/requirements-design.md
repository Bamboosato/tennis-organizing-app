# tennis-organizing-app 要件分析・設計方針

作成日: 2026-05-08

現行実装との整合確認日: 2026-10-06（package version `1.1.0`）

本書は現行リポジトリの機能・データ・API仕様を記載する。ver1.00当時の対象範囲・検証結果は[初回リリース記録](release-v1.00-scope.md)に保存する。外部サービスの本番設定と実ブラウザー動作は、ソース確認だけでは確認済みとしない。

## 1. 目的

テニス練習会向けに、ユーザー別メンバー管理、登録メンバーと当日ゲストの参加者選択、ダブルス／シングルスの対戦表作成、PDF出力を提供する。Guestログインでは人数入力による作成とPDF出力を提供する。

対戦組合せは本アプリで再実装せず、`tennis-matchup-app` の `POST /api/v1/matchups/generate` をサーバー側から呼ぶ。

## 2. 現行機能

### 2.1 認証とURL別画面

Firebase Authenticationのメール／パスワード認証と匿名認証を使う。FirebaseUIではなく独自UIを使用する。

| URL | ログイン後の画面 | Guestログイン |
| --- | --- | --- |
| `/` | アプリ説明、メンバー数、機能へのリンク | 利用可。メンバー管理の制限を説明 |
| `/members` | メンバー登録・編集フォームと一覧 | 利用不可 |
| `/matchups/doubles` | ダブルス条件入力・結果・PDF | 利用可 |
| `/matchups/singles` | シングルス条件入力・結果・PDF | 利用可 |

- 未ログインでは同じURL上にログイン画面を表示する。メールログイン後はそのURLの画面を表示する。
- 新規ID登録はメール・パスワード・確認パスワードを入力し、一致を確認する。登録後は `signOut` してログイン画面へ戻し、明示ログインする。
- ログイン画面から入力済みメールアドレスへパスワード再設定メールを送れる。
- GuestログインはFirebase匿名認証を使う。`/members` のログイン画面からGuestで開始した場合はホームへ移動する。ログイン済みGuestの直接アクセスには登録ユーザー向け画面である旨を表示する。
- ログアウト操作は認証を終了し、メンバー状態、編集中フォーム、両形式の条件・結果を初期化する。URLはそのままでログイン画面を表示する。
- アカウント表示はメールアドレスの `@` 左側、Guestは `Guest`。モーダルではメールアドレス全体または `Guest` とログアウトを表示する。

詳細なヘッダー・画面構成は[ナビゲーション設計](floating-navigation-ui-design.md)を参照する。

### 2.2 保存と状態保持

- メンバーはCloud Firestoreの `users/{uid}/members/{memberId}` に保存する。ローカル開発でもFirebase設定先へ書き込む。
- データはユーザー別に分離する。Rulesは本人のpassword providerのみread/create/updateを許可し、deleteは許可しない。
- Guestはメンバーを保存できない。登録ユーザーが入力する当日ゲストもメンバー文書には保存しない。
- メンバー非表示は `status: "inactive"` への更新であり、物理削除ではない。復元UIはない。
- 対戦表の入力条件・結果は `AppClientShell` のReact stateで、ダブルス／シングルス別に保持する。アプリ内のタブ移動では維持し、再読み込みとログアウト操作で初期化する。
- 対戦表履歴・共有URL・入力条件の永続保存は未実装。Firebase SDKによる認証状態管理と、対戦表の状態保持は別のものとして扱う。

### 2.3 メンバー管理

| 項目 | 現行仕様 |
| --- | --- |
| ニックネーム | 必須。前後空白を除去。画面入力は `maxLength=10`（HTMLの文字数制限であり、全角5文字幅の検証ではない） |
| 氏名・備考 | 任意。前後空白を除去し、未入力は空文字 |
| 性別 | `female`／`male`。フォーム初期値は女性 |
| 並び順かな | 入力欄はなく、ニックネームから辞書・正規化で自動生成 |
| 状態 | `active`／`inactive`。一覧・参加者選択はactiveのみ |
| 登録上限 | activeメンバー99人。追加時にクライアントが現在の件数を検証 |
| 編集 | 同一文書IDを維持して更新 |
| 表示順 | 登録順は `displayOrder` 降順（新しい登録が先）、アイウエオ順はかなキーを `ja` localeで比較 |

ニックネームの空文字拒否はrepositoryでも行うが、10文字制限は画面入力の制限である。件数上限・文字数・フィールド内容はFirestore Rulesで強制していない。複数端末の同時登録で99人上限を厳密に保証するトランザクションはない。

### 2.4 参加者選択とGuest人数

登録ユーザーはactiveメンバーのチェックと女性／男性の当日ゲスト人数を入力する。プルダウン内は仮選択とし、`OK` で確定、`キャンセル` で破棄する。`全選択` は現在の並び順の登録メンバー全員、`選択解除` は登録メンバーのチェックを解除する。

- 登録ユーザーの初期状態は未選択、当日ゲスト女性0人・男性0人。
- 登録ユーザーの `OK` は登録メンバーと当日ゲストの合計30人超過を拒否し、操作行にエラーを表示する。
- Guestログインの `メンバー選択` は女性人数・男性人数の入力のみ。初期値は女性4人・男性4人。各入力は0–30で、合計30人超過は生成ボタンの無効化・生成時検証で止める（`OK` 時の合計上限検証は登録ユーザーと異なる）。
- 人数入力は増減ボタンと直接入力に対応し、フォーカスを外した時に入力範囲へ補正する。
- 当日ゲストは女性から先に `ゲスト01` から採番し、男性は後続番号にする。IDはGuestログインで `guest-01`、登録ユーザーへの追加で `member-guest-01`。
- APIへ渡す `name` はニックネームまたは `ゲスト01`。`gender` は別フィールド。性別記号を名前に埋め込まず、画面・PDFの表示時に `F`／`M` を付ける。
- 入力欄横に選択人数と男女別内訳を表示する。`Summary` は参加者数・使用可能コート数・実施回数を表示し、ゲストがいる場合は次行に `01-05:女性、06-09:男性` のような採番内訳を表示する。

メンバー99人上限と対戦表参加者30人上限は別制約である。

### 2.5 対戦表作成

| 条件 | ダブルス | シングルス |
| --- | --- | --- |
| `matchFormat` | `doubles` | `singles` |
| 参加人数 | 4–30人 | 2–30人 |
| 1コートの人数 | 4人 | 2人 |
| モードUI | 通常／同性対決優先／混合対決優先 | 表示しない |
| UIから送る `matchupMode` | 選択したモード | `standard` |
| 使用可能面数 | `floor(参加人数 / 4)` | `floor(参加人数 / 2)` |
| 結果 | A／Bのペア | `player1 vs player2` |

共通条件はコート1–8面、実施1–20回。開催名は任意で、初期値は `週末テニス会`、コート数は2面、実施回数は4回。ダブルスの初期モードは通常。

| ダブルスの画面表示 | API値 |
| --- | --- |
| 通常 | `standard` |
| 同性対決優先 | `sameGenderPriority` |
| 混合対決優先 | `mixedDoublesPriority` |

条件を満たす場合のみ生成ボタンを有効化する。入力した面数が使用可能面数を超える場合、`コート数：○○面で対戦表を作成します。` の確認を表示し、`OK` で減算した面数を送る。`キャンセル` は生成を中止する。コート入力値自体は変更せず、Summaryは使用可能面数を表示する。

生成開始操作で既存結果をクリアする。通信中は同じ形式の生成ボタンを無効化し、成功後は結果と約3秒の完了トースト、失敗時はエラーを表示する。

結果はラウンド別にコートと休憩者を表示し、末尾にseedを表示する。登録ユーザーの休憩カードはコート群の下、Guestログインはコートの横スクロール領域の右側に配置する。性別記号は両形式・両ログイン方式で共通。

### 2.6 PDF出力

両形式・両ログイン方式で、生成結果の `PDF作成` からブラウザー側で保存する。日本語フォント `/fonts/NotoSansJP-VF.ttf` を読み込み、jsPDF／jspdf-autotableでA4縦のPDFを作る。

- 1行最大2コート。3コート以上は同一ラウンド内で2コートずつ折り返す。
- ダブルスは `R | A | B | A | B` を基本とし、各ペアを1名ずつ2行で表示する。
- シングルスは各コートの2列を結合し、`佐藤 F vs 田中 M` のように表示する。見出しは `Match`。
- 各ラウンドの下にコート群と同じ幅の休憩欄を付け、休憩者がいない場合は `なし`。休憩者は参加者一覧の順で表示する。
- ヘッダーは開催名、ROUNDS、COURTS、PLAYERS、SEED。フッターはアプリ名とページ番号。
- モデルのページ分割は1ページ30行の予算を使い、1ラウンドを `2 × ceil(コート数 / 2) + 2` 行として扱う。1–2コートは7ラウンド、3–4コートは5ラウンド、5–8コートは3ラウンドがモデル上の目安。実際の描画は文字幅・表の高さにも依存する。
- 開催名は幅に応じて省略し、表セルにも `ellipsize` を使用する。長い名前・休憩者多数で全文表示や任意の折返しを保証する仕様ではない。
- ファイル名は `開催名_人数人_面数面_通常-matchup.pdf` の形式。ダブルスのモード部分は `通常`／`同性`／`混合`、シングルスは `シングルス`。開催名のファイル名禁止文字を除去する。
- PDF生成中はボタンを無効化し、失敗時は再試行を促すエラーを表示する。

[2コート](pdf-layout-portrait-2-courts.png)・[3コート](pdf-layout-portrait-3-courts.png)の画像とSVGはダブルスの設計例であり、最新の性別表示・シングルスの出力証跡ではない。

### 2.7 PWAと分析

Manifestの起動URLは `/`、表示モードは `standalone`。productionのみService Workerを自動登録する。キャッシュは `/_next/static/`、`/brand/`、`/icons/`、`/fonts/` の同一origin GETを対象とし、HTML・API・FirebaseデータはService Workerのキャッシュ対象外。

standalone起動ではブランドロゴを約1.2秒表示し、320msでフェードする。表示済みフラグはsessionStorageで管理し、同一セッションの再読み込みでは再表示しない。通常のブラウザー表示では出さない。保存が利用できなくても画面利用を妨げない。

完全オフライン対応、独自インストールバナー、Push通知、Background Syncは未実装。[PWA設計](pwa-service-worker-design.md)に詳細を記載する。

ルートlayoutにVercel Analyticsを配置する。Firebaseの `measurementId` は設定項目にあるが、Firebase Analyticsの初期化は行っていない。

## 3. 画面・アクセシビリティ方針

ブルー系の背景・枠・主操作を使用する。エラーは赤文字とメッセージ、無効な操作はdisabledと補足文言・titleで理由を示す。PCはタブ、スマホは全画面メニューを使用し、メニュー中は背景スクロールを抑止する。

キーボード操作、フォーカス可視性、長い文字列、スマホのドロップダウン・固定ヘッダーとの重なり、PDFの可読性は確認対象とする。全要素で16px本文・44pxタップ領域を保証する実装ではないため、これらは改善時の目標として扱う。

## 4. データ設計

### 4.1 Firestore文書

実装が作成・更新する文書は `users/{uid}/members/{memberId}`。親の `users/{uid}` にprofileを作成する処理はない。Rulesが親パスに許可を持つことと、profile保存機能があることは区別する。

| フィールド | 保存内容 |
| --- | --- |
| `nickname`, `fullName`, `note` | trim後の文字列。任意項目の未入力は空文字 |
| `gender` | `female`／`male` |
| `sortKeyKana` | 自動生成した並び順キー |
| `status` | `active`／`inactive` |
| `displayOrder` | 登録時の `Date.now()` 値 |
| `createdAt`, `updatedAt` | クライアント生成のISO日時文字列 |
| `createdAtServer`, `updatedAtServer` | Firestoreの `serverTimestamp()` |
| `deactivatedAt` | 非表示時のISO日時文字列 |

一覧は `displayOrder` 昇順のsnapshotを購読し、画面側でactive抽出と表示順の切替を行う。サーバー日時はDBへ保存するが、現行の `Member` モデルへは取り込まない。

### 4.2 Memberモデル

`src/features/members/model.ts` の `Member` は文書IDを `id` として保持し、氏名・備考・かなキーを含む文字列フィールドを持つ。`deactivatedAt` は任意。編集してもIDを変えず、APIの参加者IDに利用する。新規登録・編集時に読み順キーを再生成する。

## 5. アプリ構成とAPI

### 5.1 主な実装箇所

| 責務 | 実装 |
| --- | --- |
| ルートlayout、metadata、PWA・Analytics配置 | `src/app/layout.tsx` |
| 認証、画面切替、入力状態、ヘッダー、フォーム、結果 | `src/app/AppClientShell.tsx` |
| URLエントリー | `src/app/page.tsx`、`src/app/members/page.tsx`、`src/app/matchups/{doubles,singles}/page.tsx` |
| Firebase初期化 | `src/lib/firebase/client.ts` |
| メンバー保存・購読・読み順 | `src/features/members/` |
| Guest採番・人数内訳 | `src/features/guests/` |
| サーバーAPI proxy | `src/app/api/matchups/generate/route.ts` |
| 表示名・Summary・PDF | `src/features/matchups/`、`src/hooks/useMatchupPdfExport.ts` |
| PWA | `src/app/manifest.ts`、`src/components/pwa/`、`public/sw.js`、`next.config.ts` |

URLエントリーのpageコンポーネントはnullを返し、共通layout内の `AppClientShell` がpathnameに合わせて画面を描画する。認証・フォームの実装位置は `src/app/page.tsx` ではない。

### 5.2 API proxy契約

ブラウザーは `POST /api/matchups/generate` にJSONを送る。

| 項目 | 検証・正規化 |
| --- | --- |
| `eventName` | 文字列はtrim。未指定は空文字 |
| `matchFormat` | `doubles`／`singles`。未指定は `doubles` |
| `matchupMode` | 3種のモード値。未指定は `standard` |
| `participantCount` | 整数。ダブルス4–30、シングルス2–30 |
| `participants` | 件数が `participantCount` と一致する配列 |
| `participants[].id/name` | 文字列・trim後に非空 |
| `participants[].gender` | 未指定または `female`／`male`。ダブルスの性別優先モードでは必須 |
| `courtCount` | 整数1–8 |
| `roundCount` | 整数1–20 |

UIはシングルスで `standard` を送るが、proxy自体は他の既知モード値をシングルスでも受理する。使用可能コート数への減算はUI側で行い、proxyは1–8の範囲のみを検証する。

上流は `MATCHUP_API_BASE_URL`（既定 `https://tennis-matchup-app.vercel.app`）の `/api/v1/matchups/generate`。`Authorization: Bearer MATCHUP_API_KEY` を付け、`cache: "no-store"` で送信する。

| 応答 | 内容 |
| --- | --- |
| 400 `INVALID_JSON` | JSON解析失敗 |
| 422 `VALIDATION_ERROR` | 入力条件・参加者の検証失敗 |
| 500 `SERVER_CONFIGURATION_ERROR` | APIキー未設定 |
| 上流のエラーstatus | 上流JSONを返す。JSONがなければ `MATCHUP_API_ERROR` |
| 502 `MATCHUP_API_RESPONSE_INVALID` | シングルスの成功応答が期待形式と不一致 |
| 502 `MATCHUP_API_UNREACHABLE` | 接続失敗など、上流呼び出し中の例外 |
| 成功 | 上流のJSON（`data` に条件・seed・rounds）を返す |

シングルス成功応答では `conditions.matchFormat === "singles"`、`playersPerCourt === 2`、rounds／courts配列、未使用ではないコートの `singlesMatch.player1Id/player2Id` を検証する。ダブルスには同じ応答形式検証を行っていない。

proxyにはFirebase ID tokenの検証、明示的なタイムアウト・リトライ・Abort制御、参加者ID重複の検証は実装していない。画面のログイン制限とサーバーAPIの認証保証を混同しない。

## 6. 優先度

| 優先度 | まず防ぐ不具合 |
| --- | --- |
| 致命 | 他ユーザーのメンバー読み書き、APIキー露出、入力と異なる参加者・形式での生成 |
| 重大 | Guest制限漏れ、人数境界の誤判定、形式別状態の混在、上流形式不一致、PDFの対戦者欠落 |
| 軽微 | かな順の期待差異、長文表示の読みにくさ、PDF余白・文字サイズ |

## 7. テスト設計

### 7.1 観点一覧と前提

ケース詳細化の前に以下を確認する。

| 観点 | 主な対象 |
| --- | --- |
| 機能 | 認証、URL別画面、メンバーCRUD、参加者選択、両形式の生成、PDF、PWA |
| 非機能 | ユーザー分離、キー秘匿、端末・OS・ブラウザー・ネットワーク差、低速通信、非同期競合、PDF可読性 |
| データ | メンバー0/98/99/100人、参加者0/1/2/3/4/30/31人、各コート・回数境界、未指定性別、長い名前、active/inactive |
| UI | 無効理由・エラー位置、男女別内訳、スマホの固定ヘッダー・メニュー、性別記号、両形式のPDF |

前提は登録ユーザー2名・Guestを分け、専用のFirebase検証projectまたは別途設定したEmulatorを使い、各ケースのメンバー数と選択状態を準備する。APIの成功・失敗は上流をmockして再現可能にする。本番メンバーの変更を自動テストの前提にしない。

### 7.4 境界値

| ID | 値 | 意図 |

### 7.6 自動化の現状と実行・証跡

- Vitest: API proxy、Guest採番・内訳、参加者名・Summary、PDFモデルの既存テスト。
- Playwright: Chromiumのみ。`e2e/pwa.spec.ts` のmanifest、SW配信・静的キャッシュ／API非キャッシュ、スプラッシュ、アイコンURLの5ケース。
- 認証・メンバーCRUD・Firestore RulesのEmulatorテスト、生成操作全体、ナビゲーション全体、クロスブラウザー、PDF描画の画像比較は既存自動テストに含まれていない。
- CIはlint、型検査、Vitest、build、Chromium E2E、auditを実行する。ローカル手順は[README](../README.md#検証)を参照。
- E2E範囲は変更リスクに応じて未実施／対象のみ／クロスブラウザー／全件を選ぶ。同一端末では直列実行し、既存サーバー再利用時はビルドの鮮度を確認する。
- 実行順序、データ初期化、環境、対象ケース、未実施範囲、結果と再現手順を記録する。Playwrightのtrace設定は `on-first-retry`（retryした場合）であり、常にtraceを保存する設定ではない。
- フレークは状態残留・非同期完了待ち・通信・端末負荷の仮説を分けて再現し、テスト観点不足／データ問題／環境問題／実装問題に分類する。
- APIエラーの確認にはstatusとerror codeを使う。proxyに構造化されたリクエスト要約ログの実装はないため、ログ取得方法は別途用意する。
